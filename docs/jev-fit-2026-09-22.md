# TypeSafe AI Jev 对 VideoAutoCut 的适配调研（2026-09-22）

> 用户最终指定目标为 **TypeSafe AI Jev（typesafe.ai）**。调研只读取官方网页、文档与官方 GitHub，以及仓库内的 [Agent 判断环节现状](agent-stage-map-2026-09-22.md)；未注册账号、调用 API、安装 SDK、下载模型或修改 VideoAutoCut。`jevai.org` 是社区站，不作为能力或性能依据。来源核对日期为 2026-09-22。

## 一页结论

**结论：Jev 值得做一个小范围、可回滚的旁路试验，但它不是 VideoAutoCut 的视觉模型替代品，也不能直接承担文案或检索词生成。** Jev 1.13 接受文本或由文本值组成的 JSON，输出预先定义好的 `Choice`、`Score`、`Noul` 决策。官方明确写明不支持图片、音频或视频输入，并且不生成文本。因此它适合包装模板选择、是否升级到强视觉 judge、是否需要二次复核等封闭判断；不适合直接替代素材方向判断、素材语义 judge、字幕安全区判断或任何需要看真实帧的环节，也不能直接生成包装文案或 1–3 条新检索词。

最稳妥的第一个试点是**包装版式选择的 shadow 模式**：仅当脚本已有 `card_content` 时，把现有纯文本/几何状态提交给固定的模板 `Choice(title/parameters/cta)`，只记录 Jev 的答案与概率，不改变现有结果。`show` 仍由脚本控制，Jev 不生成 `reason`、title 或 card 内容；任何低置信、超时、错误或分歧继续走当前 DashScope/确定性回退。该点职责封闭、默认关闭、失败路径已经存在，最容易验证类型正确性和中文准确率。它本身不是当前主耗时，进入 shadow 实验不等于已经证明提速或可以生产替换。

若目标是端到端提速，第二阶段可旁路验证“**是否升级视觉 judge**”的结构化路由：只读取向量分、来源、分差、缓存状态等元数据，高置信时减少不必要的强视觉调用，其他情况全部交回现有视觉链。历史 7 镜数据显示 orientation 约 72.875 秒、judge 约 173.484 秒、agent 总计 334.82 秒；两项必须看帧的判断合计 246.359 秒，约占 agent 总时长 **73.6%**。Jev 只能帮助减少其中一部分调用，不能完成这些视觉判断。按 Amdahl 定律，如果被 Jev 替换的判断只占总耗时很小比例，即使该判断快很多，整条链也不会显著提速。

## 官方能力与边界

| 项目 | 官方证据与结论 | 对 VideoAutoCut 的含义 |
|---|---|---|
| 定位 | [发布说明](https://typesafe.ai/blog/introducing-system-one-models-and-jev)称 Jev 是首个 System One 模型：输入状态，输出带概率的类型化决策；牺牲字符串生成以优化结构化判断。 | 适合“智能 if/route/score”，不等同聊天模型或完整 agent。 |
| 输入模态 | [Models](https://docs.typesafe.ai/models)与[State](https://docs.typesafe.ai/concepts/state)明确：仅文本；`state` 可为字符串、JSON 对象或文本数组；不支持 image/audio/video，非文本必须先转成文本或结构化字段。 | 不能直接看视频帧、拼图或成片。把视觉模型的描述转成文本再交 Jev，只能判断描述，不能核验画面事实。 |
| `Noul` | [API reference](https://docs.typesafe.ai/api)：是 yes/no 问题，返回“yes”的概率 `0..1`。官方 API 没有另一个独立 `bool` primitive。 | 可用于 `needs_review`、`upgrade_to_visual` 等路由；本项目的 `show` 继续由脚本控制。阈值由业务代码决定。 |
| `Choice` | 从调用方给定的最多 255 个选项中选最高概率项，同时返回所有选项的概率分布与 confidence。 | 适合 `title/parameters/cta`、有限路由、候选编号选择；不能产生列表外的新文案。 |
| `Score` | 对 2–10 个有序等级评分，返回各等级概率、legend、confidence，以及概率加权后的数值，数值可落在等级之间。 | 可评相关性或风险等级；不应把它当精确数值计算器。 |
| 并行问题 | 同一请求中的问题共享一个 state、独立并行评估。 | 可把模板、是否升级、是否二次复核等多个原子问题合到一次调用，但不要把相互依赖的多步推理硬塞成一个问题。 |
| 生成、多轮、工具 | [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)明确不训练文本生成；强行链式 Choice 生成会慢且效果差。多轮记录可作为 state 数组输入，但未见官方证据表明模型有会话记忆或自主多轮。官方 cookbook 的 function calling 是由代码把封闭选择映射到普通函数，不是 Jev 自主调用工具。 | 现有生成模型可继续负责检索词和代码生成；包装文案只取脚本原文，Jev 只做决策。Pi 仍是编排层候选，不能因接入 Jev 就视为已全面接管。 |
| 已知质量边界 | 官方说明英文是主要训练语言，CJK 可处理但准确率较低；长而无关的 state 会降低准确率；模型对字面表述、数字、日期、多层间接推理较弱，应把算术、约束和结构不变量留在代码中。 | 必须用真实中文脚本单独验收；原文逐字校验、分数计算、路径/数量约束继续由现有代码执行。 |

## 部署、成本、许可与数据边界

- **可用方式**：托管接口 `POST https://api.typesafe.ai/v1/systemone`，Bearer API key；官方提供 [Python SDK](https://github.com/typesafe-ai/typesafe-sdk-python) 和 JavaScript SDK。稳定别名 `jev-latest` 当前指向 `jev-1.13.0`。正式试验应固定版本号并记录响应中的版本，避免别名升级改变阈值行为。
- **价格与限额**：官方 [Models](https://docs.typesafe.ai/models) 当前列出输入 `$0.042 / 1M tokens`、输出免费；64k 总上下文，同时有“state + 最长问题”32k限制；250,000 tokens/s、1,200 requests/min。限额会动态调整，不能当长期 SLA。
- **权重与本地部署**：未找到官方模型权重、官方模型卡下载、自托管镜像或本地推理说明。公开材料只给托管 API，因此未公开本地硬件要求。官方 SDK 是 MIT，并不代表 Jev 模型权重开源或获得同样许可；模型/服务许可按客户协议，公开信息不足以推断更多。
- **数据处理**：官方 [Privacy Policy](https://typesafe.ai/legal/privacy-policy)称服务会接收 prompts/data/instructions 等 Input，不用 Input 训练或微调模型，除服务提供商外不向第三方披露 Input；服务托管在美国，并按提供服务或商业需要保留数据。[Legal](https://docs.typesafe.ai/legal)另称企业客户可申请 ZDR。公司素材、脚本或客户数据上线前仍需确认合同、保留周期、跨境和 ZDR，而不能只依据“不训练”就认定数据不落地。

## 速度主张应怎样理解

官方发布文称 Jev 端到端响应约 **70–500 ms**，在相同 System One 形状任务上约 **40–200×** 更快；首页工作流结果中的 **193.6× faster、444.6× cheaper** 也来自厂商自己的 workflow eval，官方自己说明这是实际收益的较高端。

这些数字属于**厂商测量，不是本项目可复现结论**：

- 速度是在美国西海岸笔记本调用当前位于西海岸的服务测得；公开页未给服务端 GPU/硬件、并发、batch size、网络分位数、重复次数或每个样本的上下文 token 分布。
- [Workflow evals](https://evals.typesafe.ai/)把四个厂商设计的工作流等权平均，参考答案是 GPT-6 Astra 与 Claude Fable 5.1 高思考结果的平均；其他模型使用各提供商默认 reasoning，并通过 TypeSafe 的 System One wrapper 输出同一结构。官方也承认工作流由其模型能力团队制作，可能存在偏差。
- 发布页的 side-by-side 使用短、密集 state，官方明确说这对 Jev 有利。公开静态页面没有足够信息还原完整 baseline 版本、逐任务样本量和所有原始计时。
- `70–500 ms`是完整结构化决策的端到端响应，不是 TTFT；Jev 不做逐 token 文本生成，所以拿 TTFT 与它比较本身不合适。

因此 VideoAutoCut 只能用相同机器、相同中文真实数据、相同网络和相同 fallback 规则测自己的 p50/p95 与整任务 wall time，不能把官方倍数写入产品验收或 issue 的预期收益。

## 最小、可回滚验证方案

1. **固定数据与版本**：从既有真实脚本选 30–50 个包装决策样本，覆盖缺字段、边界时长、中文歧义和无需展示；固定 `jev-1.13.0`。不要上传原始视频或无关整份脚本，只发完成决策所需的最小文本字段。
2. **只做旁路**：现有流程照常产出；只有存在 `card_content` 的样本才让 Jev 回答 `template: Choice(title/parameters/cta)`。`show` 仍取脚本字段。不让 Jev 修改 plan、文案、素材选择或渲染参数。调用失败、超时、低置信或输出缺失时记录 `fallback`，主流程不受影响。
3. **先定标签再看结果**：由当前确定性规则/已验收强模型结果加人工复核形成 gold；指标包括模板准确率、重复输入一致率、低置信覆盖率、schema 错误率、fallback 率。脚本文案被改写数必须为 0；Jev 本就不应输出文案。
4. **同时量性能**：逐调用记录输入 token、远端 RTT、p50/p95、冷启动/重试、并发、成本；同时记录单镜和整任务 wall time。比较“当前调用”“Jev shadow”“假设放权且包含 fallback”三种口径，防止只报模型响应时间。
5. **放权门槛**：先只在高置信且历史验证稳定的区域采用 Jev；其余继续当前路径。阈值用留出的真实中文验证集确定，不照搬官方示例。任何版本变化重新校准。
6. **第二试点优先做 `keep/rewrite` 路由**：Jev 只判断原 query 是否足够；若为 `rewrite`，仍由现有生成模型生成查询词。再之后才评估视觉升级路由：输入候选元数据与既有分数，输出 `use_rules / call_visual_judge / placeholder` 的 Choice，并以强视觉 judge 结果衡量“错误直通率”。目标是少调用，而不是让 Jev 声称看过画面；错误直通必须接近 0。

## 不宜替换的点

- **素材方向 orientation**：输入是真实抽帧拼图，历史 7 镜 72.875 秒；Jev 无视觉输入。
- **素材语义 judge/ranking**：必须同时看分镜语义和候选真实帧，历史 7 镜 173.484 秒；Jev 只能做前置路由或基于已有文本描述的二次分类。
- **字幕安全区、动画预览审核**：需要看帧或预览，不能由文本模型直接验收。
- **检索词/包装文案生成**：Jev 不生成字符串。它可判断“保留原 query 还是升级生成模型”，或从预先生成的候选中选择。
- **确定性校验**：原文逐字、数字、日期、数量、目录边界、分辨率和安全规则继续放在代码中；官方也明确建议算术与结构不变量由代码负责。

## 本地证据口径

本地现状来自仓库内 [Agent 判断环节现状](agent-stage-map-2026-09-22.md)，其数字是既有 Windows 历史记录或明确标注的估算，本次未重跑：搜索词改写约 2.351–3.982 秒/镜，搜索约 2.732–9.750 秒/镜，orientation 约 9.234–11.950 秒/镜，judge 约 21.723–28.430 秒/镜；7 镜 agent 总计 334.82 秒。Pi 当前只在 material 与 packaging 有显式可选 backend，默认仍是 DashScope；“已安装 Pi”不等于所有 agent 已由 Pi 编排。
